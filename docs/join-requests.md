# Join requests and owner review

## Named-home app workflow

Signing in to a named home creates or resumes one own-account access request and shares only that exact request file with the configured owner, as disclosed on the login screen. A confirmed request share shows **Your request to join this home has been sent** and a pending page with no home records. The applicant can use **Check for approval**; an uncertain request stays unconfirmed and **Retry request** resumes the same operation. It never creates another home or grants membership. An optional prompt can ask the applicant's own Fulcra-connected agent to check read-only every 30 minutes if scheduling is available. Joining does not require an agent or GitHub.

The owner opens **Household → Join requests**, selects the applicant and role, reviews the exact curated contents and confirms the recipient/scope. **Approve access** saves the bound decision and applies it through the persistent backend without an agent. **Continue access setup** resumes an interrupted saved operation. A decision save alone is not applied access. The applicant verifies membership and actual access through a fresh own-account read. See [web joining](web-joining.md) for the service, request recovery and outcome contract.

Confirmed exact-file shares become discoverable in the owner's dashboard, with an attention badge on open/refocus or **Refresh requests**. There is no off-app email/push notification. The automatic named-app route creates the request share; the manual compatibility route below requires separate applicant consent. The inbox itself is read-only.

## Manual compatibility workflow

Use this section only for a custom/manual integration explicitly using the request/review APIs or guarded CLI executor. These APIs remain available, but they are not additional steps required in the named-app workflow above. In this compatibility path, an applicant without current access can save a request and use the manual applicant prompt. There is no new-home provisioning or automatic membership.

A custom client supplies the requested viewer/contributor role and a short introduction to `POST /api/home/join-request`. This manual save writes only `/shared/home-twin/<home-id>/join-requests/<content-derived-request-id>-<sha256>.json` in that applicant's account. Authenticated identity and configured home/owner replace client identity/path claims. Introductions are self-reported evidence. Save confirmation requires exact readback; pending saves keep the same ID. The ID is derived from the normalized intent, including a declared timestamp that the browser freezes for retries; the timestamp is labeled requester-provided, not a trusted server clock. The full SHA-256 also binds the filename and request code. Changed payloads cannot reuse the same ID, even while an earlier upload is invisible. Identical retries can create identical retained versions while storage visibility is delayed; this is not an atomic exactly-once upload guarantee. Downstream execution must recheck exact hashes and current versions.

The code is `<home-id>:<requester-uuid>:<request-uuid>:<sha256>`. It is a reference, not an authentication secret or grant. The manual applicant prompt asks their own agent to verify the record, obtain specific consent and share ONLY this exact request file read-only/no history with the configured owner. Passing the code and creating that share are separate actions. Manual save/review APIs send no email/message/mesh notification and create no share; the automatic named-app service has its separate disclosed request-sharing workflow.

After the applicant explicitly shares the exact request file, the current owner sees it under **Household → Join requests**. An attention badge appears beside Household and a banner appears across the dashboard when a request needs attention. Discovery runs when the owner opens or refocuses the app; **Refresh requests** checks manually. Saving privately alone does not reach the owner. There is no off-app email, push alert or background delivery service. A pasted code under Review a join request remains a fallback. The server reads only that exact file from the coded source account using the owner's current token, with an 8 KiB streaming cap. Exact raw bytes must match the coded SHA-256. Home ID, owner, content-derived request ID, schema and authenticated stored author must match the coded source. Other accounts cannot review. Private no-store responses retain the original request digest and current home version/hash/revision.

A custom client submits the owner-selected role, decision and explicit account/scope confirmation to `POST /api/home/join-review`. It records a content-derived-ID approval or rejection intent in the owner's private home root `join-decisions/`. These are API operations, not additional buttons in the current dashboard. Current request and home hashes/version must match the reviewed preview. Version 2 also binds exact curated publication contents shown to the owner. See [publication preview and admission packet](admission-packets.md). The private review filename also contains its full SHA-256. A retry retains the same decision and declared owner-provided timestamp; uncertain readback is not confirmed approval. Invisible earlier uploads cannot authorize changed decisions under the same ID, although identical file versions can be uploaded again. No accepted snapshot, membership, publication or share is written by these routes.

Approval scope is precisely the future curated `/shared/home-twin/<home-id>/home.json` publication, with no original evidence or file history. The designated maintainer must review its actual contents and publish/share it in a separate guarded transaction before access becomes active. Private vaults, entire projects and arbitrary source paths are excluded. Selected original evidence requires separate owner consent and safe publication. Contributor return contributions/evidence and optional mesh require the member's own separate consent. A saved approval is `reviewed-awaiting-publication-and-share`; it is not a granted role, connected mesh or delivery receipt.

The manual request/review routes do not apply these review intents; the named app's persistent backend separately applies the dashboard-approved operation. Do not grant access from an unchecked JSON decision or a peer message. The executor must verify current authenticated owner, exact request source/hash, current canonical baseline, immutable decision, intended recipient/scope and exact publication/share readback, preserve originals/history and resolve uncertain intents before new writes. Changes or contradictions are held for review. Genuine two-account grant/read/contribute/revoke/mesh acceptance remains required before claiming household collaboration is verified.

## Owner inbox contract

The read-only `/api/home/join-inbox` endpoint requires the configured current owner, the caller's token and a matching canonical home. It discovers only incoming direct, untimed, read-only exact-file grants for this home's request prefix; it never reads unrelated shares, broad folders or private applicant records. Duplicate grant references are deduplicated, exact request hashes and content-derived IDs are verified, and current grants are checked again before returning. Responses are private and not cached.

The inbox compares hash-verified private owner decisions with current membership and canonical versions. Unreviewed requests, approvals awaiting application, stale approvals and conflicting decisions need attention; a rejection or a recorded role is distinguished from verified delivered access. A current approval is recognized even when older consistent approvals are preserved. Nothing is granted or published by discovery.

Checks are bounded to 20 request files, 100 owner decision files, 8 KiB per file, 1 MiB per metadata response and a 20-second reader deadline. Partial listings, unsupported related grants, unreadable files and unverified decision history are shown explicitly. Unknown grant metadata or listing outages return an unavailable check, never an empty inbox. For more requests, inspect the remaining exact shares deliberately or use a specific request code; an owner agent is an optional inspection tool. A genuine second-account share/discovery/review/access/revoke pilot remains required before claiming end-to-end delivery.


## Owner agent discovery

`node scripts/home-join-inbox.mjs inspect HOME_ID EXISTING_PRIVATE_MAINTAINER_STATE --root /PROJECT/twin` exposes the same read-only validation to continuous owner agents without an app session. An explicitly migrated legacy root uses `--legacy-root`. The command requires the caller's authenticated ownership and the existing same-home state checkpoint; it acquires the same `.cycle.lock` as other maintainer operations, then rechecks canonical version/raw bytes after discovery. It never steals a lock or changes accepted facts, shares, membership, approvals or permissions.

A changed result writes a content-bound private immutable report and updates its separate inbox checkpoint atomically; prior reports/observation times survive retries. Identical verified results emit no output. Failures leave the previous report intact and exit nonzero; that prior observation must not be presented as a fresh check. Report/checkpoint corruption, symlinks and unsafe permissions are explicit holds. Run audited home/source intake separately; this command installs no schedule and sends no notification. The owner review/application and real two-account acceptance requirements remain unchanged.
