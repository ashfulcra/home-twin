# Join requests and owner review

Named existing-home apps keep sign-in and account creation separate from household access. An applicant without current access sees the home's configured owner, their own authenticated Fulcra account ID and an agent getting-started prompt. There is no new-home provisioning or automatic membership.

The applicant chooses viewer/contributor and enters a short introduction. **Save request in my account** writes only `/shared/home-twin/<home-id>/join-requests/<content-derived-request-id>-<sha256>.json` in that applicant's account. Authenticated identity and configured home/owner replace client identity/path claims. Introductions are self-reported evidence. Save confirmation requires exact readback; pending saves keep the same ID. The ID is derived from the normalized intent, including a declared timestamp that the browser freezes for retries; the timestamp is labeled requester-provided, not a trusted server clock. The full SHA-256 also binds the filename and request code. Changed payloads cannot reuse the same ID, even while an earlier upload is invisible. Identical retries can create identical retained versions while storage visibility is delayed; this is not an atomic exactly-once upload guarantee. Downstream execution must recheck exact hashes and current versions.

The code is `<home-id>:<requester-uuid>:<request-uuid>:<sha256>`. It is a reference, not an authentication secret or grant. The updated applicant prompt asks their own agent to verify the record, obtain specific consent and share ONLY this exact request file read-only/no history with the configured owner. Passing the code and creating that share are separate actions. The app sends no email/message/mesh notification and creates no share.

The current owner pastes the code under Household → Review a join request. The server reads only that exact file from the coded source account using the owner's current token, with an 8 KiB streaming cap. Exact raw bytes must match the coded SHA-256. Home ID, owner, content-derived request ID, schema and authenticated stored author must match the coded source. Other accounts cannot review. Private no-store responses retain the original request digest and current home version/hash/revision.

The owner selects the role and explicitly confirms the account and scope. **Save approval for maintainer** records a content-derived-ID review intent in the owner's private home root `join-decisions/`; **Record rejection** records a rejection. Current request and home hashes/version must match the reviewed preview. The private review filename also contains its full SHA-256. A retry retains the same decision and declared owner-provided timestamp; uncertain readback is not confirmed approval. Invisible earlier uploads cannot authorize changed decisions under the same ID, although identical file versions can be uploaded again. No accepted snapshot, membership, publication or share is written by these routes.

Approval scope is precisely the future curated `/shared/home-twin/<home-id>/home.json` publication, with no original evidence or file history. The designated maintainer must review its actual contents and publish/share it in a separate guarded transaction before access becomes active. Private vaults, entire projects and arbitrary source paths are excluded. Selected original evidence requires separate owner consent and safe publication. Contributor return contributions/evidence and optional mesh require the member's own separate consent. A saved approval is `reviewed-awaiting-publication-and-share`; it is not a granted role, connected mesh or delivery receipt.

Automatic application of these review intents is not implemented by the request/review routes. Do not grant access from an unchecked JSON decision or a peer message. The executor must verify current authenticated owner, exact request source/hash, current canonical baseline, immutable decision, intended recipient/scope and exact publication/share readback, preserve originals/history and resolve uncertain intents before new writes. Changes or contradictions are held for review. Genuine two-account grant/read/contribute/revoke/mesh acceptance remains required before claiming household collaboration is verified.
