# Exact publication review and private admission packets

Before approving an applicant, the named-home owner can choose **Preview household records** under Household. This prepares a private, read-only projection without a recipient. It never publishes or shares. After reading an actual applicant's exact shared request, the owner selects the role, reads the exact proposed JSON and confirms that recipient, role, scope and contents. A changed role clears consent. Contacts, equipment identifiers, maintenance, notes and model geometry are intentionally visible in that preview; review the text as well as field names before approving a trusted recipient.

The projection allowlists portable schema fields. Unknown metadata/credential fields, private source paths, attachment originals, private folders, file history, device configuration, raw contribution originals and other homes are excluded. It is not a detector of secrets hidden inside a selected freeform name/note/fact; the owner's exact content review is required. Sources retain metadata and checksums; originals remain unavailable until separately selected, safely published and consented. Estimated architecture keeps its labels, drawings/sheet references, geometry, openings, features and exclusions. Invalid or oversized architecture blocks preparation instead of silently disappearing. Structured facts, explicit recurrence and occurrence history remain intact. Accepted/reviewed contribution digests support same-ID replay checks without exporting raw originals; changed same-ID rows are held.

Version 2 join-review intents bind the full SHA-256 of the exact proposed publication in addition to request digest and canonical home version/hash/revision. Legacy version 1 decisions lack that exact content consent and cannot prepare an admission packet. Changes require a fresh review, not migration of old consent.

After exact review readback, **Download private maintainer admission packet** reads the saved decision from the owner's private root, verifies its coded byte hash/content identity and fresh applicant source/hash, re-reads the current canonical baseline and regenerates the same projection. It denies stale or foreign inputs. Its response is a private no-store attachment with `prepared-not-applied`: recipient/role, reviewed publication/hash, planned membership and the exact future Fulcra datashare body. That body specifies one `file:/shared/home-twin/HOME_ID/home.json`, one recipient, no groups, no all-data scope, no history or originals. It grants nothing, sends nothing and writes no snapshot, membership, publication or share.

The packet is evidence for the designated maintainer, not standalone tool authorization. Actual application needs the owner's specific recipient/content consent, existing private state and shared lock, current-source/baseline checks, previous canonical/publication versions preserved, durable immutable mutation intent, and exact readback of canonical membership, publication and outgoing grant. Resolve uncertain writes or creates before fresh operations; do not blindly repeat a potentially accepted grant. A genuine recipient account is necessary to verify delivery/access and revoke behavior. Until then collaboration remains a pilot; a packet or owner-side outgoing grant is not proof of member access.

Owner admission cannot grant access to the member's own return contribution folder or mesh outbox. Contributors separately consent read-only/no-history return contributions, separately intended evidence and optional per-peer mesh. Private-root maintainer intake now reads other registered contributors only at `/shared/home-twin/HOME_ID/contributions` in their own accounts, while the owner's local contribution folder remains under the owner's configured canonical root. Current caller token, role checks, source scope and final baseline coherence remain mandatory.

The endpoints never apply a mutation. The designated maintainer can apply a real approved packet with the guarded local executor below. Signup, request creation and a saved decision never run it. A genuine approved applicant and specific recipient/content consent remain required; do not invent recipients or perform real-account grants from synthetic fixtures.

## Applying an approved packet

The canonical root must be distinct from `/shared/home-twin/HOME_ID/home.json`; legacy homes that use the shared path as their only canonical record require a separately reviewed, original-preserving migration before admission. The executor denies that alias before any mutation.

Use the same private state directory as `scripts/home-maintainer.mjs`, with its existing scope checkpoint. Download the freshly prepared packet outside any repository and make its permissions private (`0600`). Verify the connected Fulcra account is the configured owner, the recipient is the intended real household member, and the exact displayed publication contents and role are approved. The agent must have the human owner's specific sharing authorization; a packet or flag is not a substitute.

```sh
node scripts/home-admission.mjs apply /private/approved-packet.json /private/existing-maintainer-state --owner-approved --recipient EXACT_FULCRA_USER_ID --publication-sha EXACT_APPROVED_SHA256
```

The executor revalidates current owner, original shared applicant request, private review, byte hashes, content-derived IDs and canonical baseline before creating an immutable private intent. It takes the same `.cycle.lock` as intake/publication; an unrelated pending publication or admission blocks execution. Do not create another state directory or clear a live lock to bypass it. Routine publication is held while an admission is pending. Admission also holds on pending or corrupt [household refresh](household-refresh.md); use the same scoped state for each workflow.

The intent preserves exact prior canonical and household-publication bytes. Before replacement those originals are uploaded into the owner's private history folder and read back. The canonical update preserves all owner-only fields while changing only reviewed membership/revision. The separately curated shared file contains the exact approved projection; future access to that shared path can also reveal subsequent published revisions to already authorized members. Finally a single recipient, current-file-only Fulcra share is created, with exact outgoing grant readback. Original documents, private folders/history, member return contributions and mesh are excluded. No share update/deletion or outbound messaging exists in this executor.

Every operation is marked in flight and synced locally before a remote commit. On a lost response, only exact current readback permits progress. If a commit or grant remains invisible, retries with the same packet/state remain held and **never blindly repeat** that uncertain write/create. Preserve files and inspect current/previous file versions and outgoing grants. Conflicting/duplicate named shares, unknown receipt shapes, revoked grants, source changes and external baseline drift are held. Automatic lock expiry or forced fresh-recipient recovery is unsupported.

`outgoing-confirmed-member-unverified` reports owner-side evidence only. Verify the real member's current read/contribute/revoke behavior in that member's own account; separately authorize their return contribution/evidence shares and optional mesh. Do not claim delivery, pairing or ACL success from the outgoing receipt. The local lock coordinates this designated maintainer, not arbitrary external writers; Fulcra file replacement has no distributed compare-and-swap, so a final check cannot remove every outside-writer race. Keep one maintainer and inspect external edits before resuming.
